# Blink-frame User Guide 

## Synopsis
`Blink-frame` is a variant of `Blink`. You should have a good understanding of what `Blink` requires
for setup, as this guide is for wanting to use Blink past its intended purposes.

It is meant to capture all events during a "marked" period across many blink-enabled libraries.
It only operates in Normal Mode, so no need to worry about weird kernel configuration.

Here is an example on `libwmutil`, tagged with an arbitrarily designated LIBKEY=10.
There are custom scripts that I wrote to facilate this process available, but the major steps are the following:

1. `git checkout blink-frame`
2. set `#define LIBKEY 10` (this key now represents this library)
3. set `#define REGISTER_SIGNAL 1` (0 to not register any signal handler)
4. compile the clang compiler

### Modes of operation
#### Regular Mode
In Regular Mode, the user would enable Blink's tracing on a process by running the `configure-blink` script which sends SIGUSR2 to the process to enable tracing for that process. 
Until enabled, the tracing function will simply `return` on every invocation. Once enabled the tracing function will collect PMU counter values and write them to a thread local ring buffer.

## Compiler Setup
Ensure that your BiSheng compiler is based on the `blink-frame` branch. You can find it [here](https://codehub-y.huawei.com/BiSheng-Mobile/Mobile-CPU/BiSheng/files?ref=blink-main).

## Using Blink
There are four parts of setup required to use Blink: 
1. Compile Time Setup: Passing the necessary compiler flags to BiSheng compiler for instrumentation a binary/library.
2. Post-Compilation: The compiler generates files containing information about the source code. These are required to parse the traces generated by Blink and generate user-readable reports, hence these files need to be saved.  
3. Runtime Setup: Enabling Blink tracing for a process at runtime by specifying tracing parameters.
4. Post-processing: The traces generated by Blink need to be parsed to generate user-readable reports. 

*Note*: Only one library in a process can be instrumented with Blink currently. Multi-library instrumentation support will be added later.

## Compile Time Setup
Before compiling OHOS or its associated libraries, create a folder called `MIPCodeInfo` under `out/generic_generic_arm_64only/general_all_phone_standard`, this folder will be used to store source level info as .csv files for all the instrumented locations.
It will be used in the post-processing step. When compiling a simple C/C++ file, please create this directory from where `clang/clang++` will be called.

When compiling OHOS, make warnings non-fatal by setting `fatal_linker_warnings = true` to `false` in build/config/compiler/BUILD.gn.

A user can instrument a program with Blink by compiling the C/C++ program using `clang/clang++`, linking with `lld` and passing options to enable Blink on the BiSheng Compiler as follows:

### Mandatory paramters

1. `"-fmachine-profile-generate"`, `"-Wl,-Bsymbolic"`, `-Wl,-mllvm,-enable-machine-call-graph` and `"-Wl,-mllvm,--enable-machine-instrumentation"` 
Required to enable Blink's instrumentation on the compiled program

2. `-Wl,-mllvm,--blink-mode=`
Used to specify Blink's mode of operation. Two options can be specified - `regular` or `dynamic`

*Note*: If you are running just the compiler(`clang -c`) and not the linker then use the options `"-fmachine-profile-generate"`, `"-Wl,-Bsymbolic"`, `-mllvm -enable-machine-call-graph`, `"-mllvm --enable-machine-instrumentation"` and `"-mllvm --blink-mode="` instead

### Optional parameters
1. `-blink-blacklist-functions=`
Used to specify the functions that should not be instrumented, all other functions will be instrumented. Valid values that can be specified are:
* *<function_name>*: The function whose mangled name matches <function_name> will not be instrumented
* *[<function_name1>, <function_name2> ..]*: The function whose mangled name is present in the provided list will not be instrumented. 
* Default value is \[\], i.e., all functions will be instrumented. 

*Note*: If a user wants to add `-Wl,-mllvm,-blink-blacklist-functions=foo,bar` to `ldflags`, it must be split into separate entries, like:
    `"-Wl,-mllvm,-blink-blacklist-functions=foo", "-Wl,-mllvm,-blink-blacklist-functions=bar"`
This is because `ldflags` does not support comma-separated lists for repeated flags. Same requirement goes for `-blink-whitelist-functions=`

2. `-blink-whitelist-functions=`
Used to specify the functions that should be instrumented, all other functions will not be instrumented when this option is used. Valid values that can be specified are:
* *<function_name>*: The function whose mangled name matches <function_name> will be instrumented
* *[<function_name1>, <function_name2> ..]*: The function whose mangled name is present in the provided list will be instrumented.
* Default value is the mangled names of all the functions, i.e, all functions will be instrumented.

## Post-Compilation
The compiler generates a folder called `MIPCodeInfo` containing `.csv` files that map unique IDs representing instrumented locations in the binary to source code information like function name, file name and line number.
This folder is generated from the location where the compiler is run. In the case of OHOS, this folder is generated in `out/generic_generic_arm_64only/general_all_phone_standard`. Please ensure the folder is created before compiling OHOS or its associated libraries.

This folder and the csv files are required by the post-processing script to parse the traces generated by Blink and generate user-readable reports in Post-processing stage.   

## Runtime Setup on a phone
In order to use Blink's Dynamic Mode, the phone needs to have the XPM module disabled and SELinux set to permissive mode to allow binary rewriting.
1. Disabling XPM module: Edit /etc/init/key_enable.cfg to change "write /proc/sys/kernel/xpm/xpm_mode 5" to "write /proc/sys/kernel/xmp/xpm_mode 0" and reboot the phone. Ensure the command `sysctl kernel.xpm.xpm_mode` returns 0.
2. Setting SELinux to permissive mode: Run `setenforce 0` before tracing a workload.
3. Create `/data/storage/el1/base` and run `chmod 777 /data/storage/el1/base`, this directory is required to pass configuration data if the traced process is NOT an app.
4. Send the instrumented library to the phone to its respective directory (observe no phone crash)
5. Send the `configure-blink` binary (it's available [here](https://rnd-gitlab-ca-y.huawei.com/Scope/BiShengMobileStudio/yscope/-/tree/main/blink?ref_type=heads)) to the phone.

*Note*: Do NOT run `perf` alongside Blink. This will impact the PMU counter values read by Blink

## Runtime
Tracing for the compiled program is disabled until the user enables it by running the configure binary. The configure binary can be run as:

`./configure-blink`

This binary is available in [here](https://rnd-gitlab-ca-y.huawei.com/Scope/BiShengMobileStudio/yscope/-/tree/main/blink?ref_type=heads).

### Mandatory parameters
1. `--pid`: Provide the pid of the process to be traced. If the process contains multiple libraries and only one of them is compiled with Blink, only the blink-enabled library will be traced.

2. `--event`: Provide the perf event name of the event to be traced. E.g. hw-instructions, cpu-cycles etc. For a full list of events use the `--list` options of the configure script.

3. `--mode`: Specify whether the binary or library was compiled in `dynamic` or `regular` mode.

4. `--bundle`: (Required when tracing an app) Specify the bundle name. E.g. com.huawei.hmos.photos for photos.

### Mandatory parameters in dynamic mode
1. `--lib`: Specifies the name of the instrumented library/binary. This is required for binary rewriting to toggle tracing on and off. If this parameter is omitted, Blink will not produce any output, as it lacks the mechanism to enable tracing dynamically.

### Optional parameters

1. `--output-dir`: Specifies the directory where the traced buffers will be output. The traced process should have access to write to this directory. 
* By default this is `/data/storage/el1/base `. 

*Note*: In order to trace an app, the output-dir must be set to `/data/storage/el1/base` because the app is sandboxed. The output trace files would be in `/data/app/el1/100/base/<bundle_name>`.

2. `--buffer-size`: Specifies the thread local buffer size in number of samples. One sample contains the event count for one invocation of a function, with a size of 16 Bytes. Once this buffer is full, it will be flushed to disk. 
* By default this is 10,000 samples or 160,000 Bytes. 

*Note*: Optional Parameters 3–5 have no effect if the binary or library is compiled in Regular Mode.

*Note*: In Dynamic mode, unless the `--pervasive` option is used, sampling is enabled by default with the default options.

3. `--nsamples` and `--sampling-interval`: These options are used to specify the sampling frequency of Dynamic Mode. 
`--nsamples` specifies the number of samples to collect for a function before disabling tracing, `--sampling-interval` specifies how many milliseconds to wait before re-enabling tracing for functions whose tracing is disabled (This re-enabling mechanism happens in a seperate thread that iterates over metadata of all the functions). So for `--nsamples=10 --sampling-interval=400`,  tracing is disabled after 30 samples for a function and re-enabled every 400ms.
* By default, the options are set to `--nsamples=10` and `--sampling-interval=400`


4. `--pervasive`: This is a flag that disables sampling in Dynamic mode. Once tracing is enabled, all invocations of all the instrumented functions will be traced.
* By default, this value is false.

*Warning*: Pervasive instrumentation of libraries like `libark_jsruntime.so` can generate gigabytes of trace data that can take a long time to post-process. We are actively working on speeding up post-processing with multi-threading and caching results.

5. `--max-sample`: Sets an upper limit on the total number of samples collected.
* By default, this value is 0 (no cap)

6. `--pmu-index`: Specifies the PMU counter for Blink to read.

* Supported values range from 0 to 5, as the small cores on Huawei mate series phones have only six PMU counters. By default, this value is set to 5, meaning Blink reads from register `pmevcntr5_el0`. This register is proven to be used by Blink on HarmonyOS 205.0.1.47. 
* To identify which PMU counter is in use on your version of OS, use the provided blink-pmu-detect script. Send the script to the device and run it with `./blink-pmu-detect`, and you should see the following message.
 
  `[RESULT] Counter PMEVCNTR5_EL0 appears monotonically increasing. Recommend using index 5.`

  * Caveat: Do not run lock_freq_char.sh before blink-pmu-detect as it inteferes the PMU scheduling.


## Workload
Once Blink tracing is enabled using `configure-blink`, the user can run their respective workload and instrumented library will trace the function executions.
The per-thread buffers will be flushed once full in the user specified `--output-dir`. Blink will continue running until the traced process is killed. (We will add support to stop Blink using a different signal soon)

*Note*: When tracing an app, sometimes you need to kill or force stop the app for the output traces to be visible.

## Output - Parsing
The traces generated by Blink after running a workload are output to the user specified `--output-dir` directory as `thread-<unique-tid>.bin`.
This unique-tid is the value of the register `TPIDR_ELO` for the thread which output the thread local buffer. This value is unique per thread but is not the same as the Linux thread ID (`tid`).

Each trace file contains a sequence of paired values embedded in the binary: a function encoding and a corresponding raw PMU value.
To interpret these traces, please use the post-processing script provided [here]( https://rnd-gitlab-ca-y.huawei.com/Scope/BiShengMobileStudio/yscope/-/tree/main/post_process). The repository includes detailed documentation and supporting scripts to help analyze and interpret the profiled data effectively.

## Known Issues:

### PMU Glitching
 

Throughout our testing, the per-thread trace files may occasionally contain garbage PMU reading, and the severity of the issue fluctuates with the OS we are testing on. For example, on OS 202403, we have observed this issue happened intermittenly, roughly 10% of the time. Wile moving towards a newer OS version, OS 202501, we only saw this issue happened once.

Our current hypothesis is that kernel's profiling activities may also use PMU counter, causing rescheduling to different PMU to count event rather than the one are assuming.

The provided post-processing script is designed with this issue in mind. If corrupted data is too much, the script will notify the user with the corruption message, and we kindly ask user to rerun Blink on the same workload.

We acknoweledge the current way of accessing PMU counter is not bullet-proof, and we are working on solving this issue.

## Debug Steps:

### mprotect failure
If you have not disabled XPM mode or run `setenforce 0` or if you specify the wrong library, the `mprotect` call will fail. 
The will be represented by a file called `mprotect-failure.txt` in /data/storage/el1/base (for non-apps) and /data/app/el1/100/base/<bundle-name> (for apps).
The file contents show the error no. of failure.
